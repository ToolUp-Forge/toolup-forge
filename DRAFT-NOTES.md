# Draft notes

What each change that rides or advances the core `<Version>` declared in `Directory.Build.props` tells a
consumer, one line per change, in the order the changes landed. The list below the marker is **append-only**:
a change appends ONE line at the end of the file and never edits, reorders or removes a line already in it.

    - <phase> (<version it rides>): <class> — <one sentence>

`<class>` is what the surface guard says the change is (`breaking`, `additive`, or `none`), and the sentence
names what a consumer must know, with its migration note under `docs/migrations/` if there is one. A release
keeps the list; the change that opens the next draft appends below it like any other line.

**Why here, and not in `Directory.Build.props`.** Every project imports the props, so the affected lane cannot
see past a change to it and runs every test (`msbuild-import`, `docs/platform/testing-conventions.md`). A line of
prose about a change has no business in a file that reaches every project: kept there, it put almost every
versioned change on the full lane. The props keep the `<Version>` itself, which is a real build input.

**Why here, and not in `CHANGELOG.md`.** The changelog is rendered from the release tags at release and holds
released sections only (`docs/platform/release-process.md#the-changelog-is-rendered-at-release`); `Changelog
--check` refuses a hand-written section in it. `Changelog --draft` prints the surface movement the next release
will carry; this file is the prose beside it.

**Two branches that each append a line merge without a hand resolution.** `.gitattributes` binds this file to the
`toolup-draftnote` merge driver, which `dotnet run --project Build.fsproj -- Setup` registers per clone. It runs an
ordinary three-way merge and resolves only a conflict that is a pure insertion on both sides below the marker,
ours first. Anything else, an edit to a line already in the list or to the text above the marker included, is
left with its markers.
