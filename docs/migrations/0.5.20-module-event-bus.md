# 0.5.20 — cross-module client event bus (consumer adoption)

**What changes.** `ToolUp.Platform.Client` gains a first-class seam for one client module to broadcast a named event that sibling modules react to — without either module importing or referencing the other. A publisher returns a `Cmd` from its `update`; subscribers declare a topic→`Msg` mapping at registration time; the shell fans each publication out to every subscriber's normal `update` loop.

This closes a structural gap: the shell shares a module's model across *its own* pages, but modules are otherwise isolated, so a publisher mutating its state has no way to tell a sibling module whose already-loaded model has gone stale as a result (the classic "module A finished a batch; module B still shows the pre-batch count until a full page reload").

**Backward compatible (GP 11).** The new `EventSubscriptions` field defaults to `Map.empty` and the bus has no subscribers until a module declares one — an existing app that adopts 0.5.20 and registers zero subscriptions compiles and behaves byte-for-byte as before. Adoption is purely additive and opt-in per module.

## New surface

| Symbol | Module | Shape |
|---|---|---|
| `ModuleEvents.publish` | `ToolUp.Platform.ModuleEvents` | `string -> string -> Cmd<'msg>` — `publish topic payload` |
| `ClientModule.withEventSubscription` | `ToolUp.Platform.ClientModule` | `string -> (string -> 'Msg) -> ClientModule<_,_> -> ClientModule<_,_>` |
| `ModuleEvents.subscribe` | `ToolUp.Platform.ModuleEvents` | shell-internal — `Listener -> (unit -> unit)`; consumers don't call this directly |

`ErasedModule` / `ClientModule<'Model,'Msg>` gain an `EventSubscriptions` field. Apps that build `ErasedModule` *records by hand* (rare — almost everything goes through `ClientModule.register`) must add `EventSubscriptions = Map.empty`. Apps that use `ClientModule.create |> … |> register` need no change to existing modules.

## Adoption — publisher side

In the publishing module's `update`, return `ModuleEvents.publish` as the command. Publishing stays MVU-pure — the broadcast runs in the Cmd-execution phase, not the update body:

```fsharp
// before — local state change only; siblings never learn about it
| BatchCompleted result -> { model with Pending = 0 }, Cmd.none

// after — also broadcast on a namespaced topic
| BatchCompleted result ->
    { model with Pending = 0 }, ModuleEvents.publish "myapp/classification-done" ""
```

Topics are plain strings namespaced by convention (`"<app>/<event>"`). The payload is any string the subscriber needs (`""` when the event itself is the whole signal).

## Adoption — subscriber side

Declare the subscription at registration and map the payload into one of the module's existing `Msg` values:

```fsharp
ClientModule.create { Init = init; Update = update; Name = "Watchlist"; Icon = icon }
|> ClientModule.withView view
|> ClientModule.withEventSubscription "myapp/classification-done" (fun _payload -> Refresh)
|> ClientModule.register
```

When any module publishes `"myapp/classification-done"`, the shell calls the mapper, gets `Refresh`, and runs it through the subscriber's `update` — initialising the subscriber on demand if the user has never navigated to it this session. The subscriber's model is therefore fresh the next time it renders, with no manual Refresh button and no page reload.

## Semantics

- **Identity-free routing.** Delivery is purely by topic. A module receives its own publication *only* if it also subscribes to the same topic — the common case (publish to notify others) never self-delivers. Beware a module that both publishes and subscribes to topic T and whose subscription `Msg` re-publishes T: that is an infinite loop, the same way any `update` that re-dispatches its own trigger would be.
- **No registry coupling.** Topics with no subscribers are a silent no-op. Publisher and subscriber never reference each other or a shared topic registry.
- **Inactive-target init Cmds.** If the subscriber has never been navigated to, the shell runs its `Init` to materialise state before applying the mapped `Msg`, but discards the `Init`'s own `Cmd` for inactive targets (it routes through `ModuleMsg`, which targets the active module) — the same trade-off the `ModuleAction` path documents. Subscribers whose `Init` returns `Cmd.none` (the overwhelming majority) are unaffected; any deferred `Init` work runs on next navigation.
- **No RBAC gate.** Unlike the server-driven `ModuleAction` path, the event bus is client-internal: the publisher already runs in this user's client, so every subscriber is code the same client loaded. There is no cross-tenant trust boundary to enforce.

## Verification steps (consumer adoption PR)

1. **`dotnet build`** clean on the consumer's sln.
2. **`dotnet fable -o output --noCache`** clean from the client project (Fable catches client-only breakage the .NET build misses).
3. **Behavioural.** Trigger the publishing action; switch to the subscribing module — its state reflects the change with no manual refresh and no page reload.
4. **Zero-subscription regression.** A module that registers no subscription compiles and runs unchanged.

## Worked example

`samples/MixedMode/src/Client/Client.fs` ships a `Notifier` module (publishes `"mixedmode/ping"` from a button click) and a `Listener` module (subscribes and increments a received-count) that demonstrate the seam without either importing the other.

## Rollback

The bus is additive — reverting a consumer's adoption PR (drop the `withEventSubscription` calls and the `ModuleEvents.publish` commands) restores prior behaviour exactly. The SDK surface stays shipped; an app with no subscriptions pays nothing (GP 13 — no subscribers means `fire` iterates an empty list).
