# Phase 767 — sidebar and toolkit string localization

**Consumer action required: only if you call one of three toolkit functions directly.**
`Toolup.UIToolkit.Forms.fileUpload`, `Forms.dataSourcePicker` and `StateViews.errorBanner` each
gained one caller-supplied string parameter — the three literals the `ToolUp.Platform.UI` fsproj
header recorded at the Phase 307 extraction as the toolkit's last exceptions to its
labels-passed-in posture. Everything else is additive.

## What changes

| | Before | After |
|---|---|---|
| `Client/UI/Sidebar.fs` | six user-visible literals (the Phase 444 deferral) plus the Phase 572 / 611 / 612 strings that accrued behind it — `"Pinned"`, `"Hidden items"`, `"Other"`, `"Pin"` / `"Unpin"`, `"Hide"` / `"Restore"`, `"Reorder …"`, the four reserved-row accessible-name fallbacks, `"Unnamed entry"`, `"Powered by ToolUp-Forge"` | every one reads `MessageCatalog.Sidebar`; the `Sidebar` component takes the section from `useMessages ()` and threads it through the plain render functions |
| `Toolup.Sidebar.buildSections` | titles hard-coded | **+ `buildSectionsWith (messages: SidebarMessages)`**; `buildSections` keeps its arity and its English titles (it is `buildSectionsWith MessageCatalog.english.Sidebar`), and the shell calls the `…With` form with the resolved catalog |
| `SidebarMessages` | 6 fields, minted by 444, read by nothing | **+ `HiddenItemsSection`, `OtherSection`, `Reorder: string -> string`, `HomeEntry`, `AdminHomeEntry`, `AdminAreaEntry`, `ProductAreaEntry`, `UnnamedEntry`** |
| `ShellMessages` | — | **+ `NoModulesAvailable`** (the empty-shell placeholder `Layout.AppShell` renders) **and `Loading`** (the accessible name of every `role="status"` loading region `Layout` renders) |
| `Layout.loadingSkeleton` / `loadingIndicator` / `loadingIndicatorInline` | `aria-label="Loading"` literal | the region is a private `LoadingRegion` component reading the catalog; the three public functions keep their arity |

| `Forms.dataSourcePicker label selectedFile placeholder options onSelected` | `"No data files available — upload via Data Manager"` literal | **`Forms.dataSourcePicker label selectedFile placeholder emptyMessage options onSelected`** |

## Why

Phase 444 swept the shell and recorded the sidebar as a deliberate deferral: its strings were
rendered by plain functions the toolkit extraction (307 / 344) was about to restructure, and the
extraction should decide whether the toolkit takes a catalog or stays string-free. Phase 307 decided
— string-free, labels passed in, sidebar stays in `Platform.Client` — and named the three toolkit
literals that did not yet honour it. 751 finished the module sweep and was told not to touch the
sidebar. This is the successor both of them pointed at. The skeleton is the third thing 444 left
open: a consumer authoring a second language had one docs snippet to copy and a ~1,300-leaf
`english` value to read.

## Diff to apply

**Every deployment:** nothing, unless you call one of the three toolkit functions directly. No
`ServerConfig` or `ClientConfig` field moves. A `MessageCatalogOverride` written as copy-and-update
keeps compiling: the eight new `SidebarMessages` fields and two new `ShellMessages` fields default
to English.

**A caller of `Forms.fileUpload`:**

```diff
- Forms.fileUpload "Upload" model.FileName "Choose a CSV" (FileChosen >> dispatch)
+ Forms.fileUpload "Upload" msgs.ChooseFile model.FileName "Choose a CSV" (FileChosen >> dispatch)
```

**A caller of `Forms.dataSourcePicker`:**

```diff
- Forms.dataSourcePicker "Source" model.Selected "Pick a file" options (SourcePicked >> dispatch)
+ Forms.dataSourcePicker "Source" model.Selected "Pick a file" msgs.NoDataFiles options (SourcePicked >> dispatch)
```

**A caller of `StateViews.errorBanner`:**

```diff
- StateViews.errorBanner message (Some (fun () -> dispatch Dismissed))
+ StateViews.errorBanner message msgs.Dismiss (Some (fun () -> dispatch Dismissed))
```

where `msgs` is whatever your module reads from `MessageCatalogProvider.useMessages ()` (or a
literal, if your module is not localised — the toolkit does not care where the string came from,
only that the caller chose it).

**A deployment that constructs `SidebarMessages` or `ShellMessages` as a full record literal** (not
the documented copy-and-update shape) adds the new fields; the compiler names them.

**A consumer authoring a translation** starts from the skeleton — see
[client-localization.md → Start from the skeleton](../platform/client-localization.md#start-from-the-skeleton-phase-767).

## Verification

- `LocalizationTests` (`dotnet run --project src/ToolUp.Platform.Tests -- --filter-test-list "localization gate"`):
  the swept set now includes `Client/UI/` and `src/ToolUp.Platform.UI`, and reports zero
  un-externalised literals. Pseudo-locale coverage: **1,311 leaves before → 1,321 after** (the ten
  new fields; the `Locale` root leaf is outside both counts). Go-red tests pin that a Sidebar
  literal and a toolkit literal are findings, and that the toolkit is inside the file walk.
- `docs/platform/message-catalog-skeleton.fs` compiles inside `ToolUp.Platform.Tests` and
  byte-matches the generator; the skeleton's leaf count agrees with the pseudo-locale walk.
- `VerifyFable` (241 cases, every Sidebar pack) green; `samples/MinimalClient` Fable compile clean;
  `api-baselines/ToolUp.Platform.UI.approved.txt` (three retyped signatures) and
  `ToolUp.Platform.Client.approved.txt` (record ctors + `buildSectionsWith`) regenerated surgically.

## Rollback

Revert the commit. The three toolkit signatures return to their previous arity; the
`SidebarMessages` / `ShellMessages` fields disappear (a copy-and-update override that set them
stops compiling, naming the field — the documented asymmetry); the gate's `Client/UI/` exclusion
returns with it. Delete `docs/platform/message-catalog-skeleton.fs` if it is left behind — the
test project includes it only when it exists.
