# Migration — 0.4.0 EntraExternalId companion deprecation

**Status.** Soft deprecation in `0.4.0`. The `EntraExternalId` (server) + `EntraExternalIdClient` (client) companions continue to compile and ship; the README + module-header doc comments carry a deprecation banner pointing consumers at the new path. Removal is scheduled for `0.Y.0`.

## What changed

The 0.4.0 `OidcAppConfig` unification (see [`0.4.0-oidc-app-config.md`](0.4.0-oidc-app-config.md)) ships `OidcPresets.entraExternalId` + `OidcPresets.entraExternalIdWithDomain` as the recommended path for Entra External ID (CIAM) deployments. The preset returns an `OidcAppConfig` consumed by the standard `OidcAuthUI` shell — no `CustomAuthUI` wrapping, no companion-specific config record.

The dedicated companion remains the right choice for two specific use cases the single-call preset doesn't cover:

| Use case | Why companion still wins | Preset adequate? |
|---|---|---|
| **Sign-up / sign-in user-flow policy routing** (`SignUpPolicyId` / `SignInPolicyId`) — surfaces a "Sign up" button alongside "Sign in" that routes through a separate Entra User Flow. | ~~Single-call preset has no policy-routing surface; sign-up requires the explicit shell-level "Sign up" affordance the companion provides.~~ **Superseded 2026-08-30:** `OidcAppConfig.SecondaryFlow` puts the dual-button affordance on the standard `OidcAuthUI` shell, and `OidcPresets.withEntraSignUpUserFlow` binds a user-flow policy id into it (see the second note under "When to stay on the companion"). | ~~No.~~ **Yes for sign-up, since 2026-08-30.** |
| **Server-side `oid` → `UserId` / `tid` → `TenantId` claim remapping** — External ID's `oid` is more stable than `sub` (which varies per app registration). | ~~Generic `OidcAuthProvider` uses `sub` → `UserId`; remapping to `oid` is not yet exposed as a first-class option. Tracked separately as a substrate seam.~~ **Superseded 2026-08-30:** `AuthConfig.ClaimMapping` exposes it as a first-class option (fail-closed where this companion falls back — see the note under "When to stay on the companion"). | ~~No.~~ **Yes, since 2026-08-30.** |

For everything else — basic sign-in against an External ID tenant, with or without a custom CIAM domain — the preset is now the recommended path.

## Worked migration — sign-in-only consumer

Pre-0.4.0:

```fsharp
// Client side
let externalIdCfg =
    EntraExternalIdClientConfig.create
        "<tenant-subdomain>"
        "<client-id>"
        "https://app.example.com/auth/callback"

ClientConfig.compose
    {| ...
       AuthUI = CustomAuthUI { Wrap = EntraExternalIdAuthUI.wrap externalIdCfg } |}
```

```fsharp
// Server side
let externalIdServerCfg =
    EntraExternalIdConfig.create "<tenant-subdomain>" "<audience>"

ServerApp.empty
|> ServerApp.withAuth (EntraExternalIdAuthProvider.create externalIdServerCfg ...)
```

0.4.0 equivalent:

```fsharp
// Client side
let oidcCfg =
    OidcPresets.entraExternalId
        "<tenant-subdomain>"
        "<client-id>"
        "https://app.example.com/auth/callback"

ClientConfig.compose
    {| ...
       AuthUI = OidcAuthUI (OidcAppConfig.toClientConfig oidcCfg) |}
```

```fsharp
// Server side
let oidcServerCfg : OidcAuthProviderConfig =
    { Issuer = oidcCfg.Issuer       // SAME issuer the client side built — single source of truth
      Audience = oidcCfg.Audience
      ClientId = oidcCfg.ClientId
      ... }

ServerApp.empty
|> ServerApp.withAuth (OidcAuthProvider.create oidcServerCfg ...)
```

The boilerplate around projecting `OidcAppConfig` to the server-side `OidcAuthProviderConfig` is a one-cycle bridge — a follow-up commit lands `OidcAppConfig.toServerConfig` so consumers write `OidcAuthProvider.create (OidcAppConfig.toServerConfig oidcCfg) ...` directly.

## Worked migration — custom CIAM domain consumer

Pre-0.4.0:

```fsharp
let externalIdCfg =
    { EntraExternalIdClientConfig.create "<tenant>" "<client-id>" "<redirect>"
        with CustomDomain = Some "login.mybrand.com" }
```

0.4.0:

```fsharp
let oidcCfg =
    OidcPresets.entraExternalIdWithDomain
        "<tenant>"
        "login.mybrand.com"
        "<client-id>"
        "<redirect>"
```

## When to stay on the companion

Keep the existing wiring untouched when **either** of the following applies:

1. ~~Your sign-in shell surfaces a "Sign up" button that routes through a distinct Entra User Flow (`SignUpPolicyId`). The companion's `EntraExternalIdAuthUI.wrap` is the only path that exposes the dual-button affordance today.~~ **CLOSED 2026-08-30** — see the second note below.
2. ~~Your server-side handlers depend on the `oid` claim being projected onto `AuthenticatedUser.UserId` (rather than `sub`). The companion's `EntraExternalIdAuthProvider` is the only path that performs this remapping today.~~ **CLOSED 2026-08-30** — see the note below.

> **Note added 2026-08-30 — reason 2 is closed.** The substrate gained the claim-mapping seam this document anticipated: `AuthConfig.ClaimMapping` on the generic `OidcAuthProvider` projects any named claim onto `AuthenticatedUser.UserId` / `TenantId`, with `TOOLUP_OIDC_USER_ID_CLAIM` / `TOOLUP_OIDC_TENANT_ID_CLAIM` as the env-composed route. `ClaimMapping = Some { UserIdClaim = Some "oid"; TenantIdClaim = Some "tid" }` reproduces the companion's remapping on every token that carries those claims, verified against the companion's own fixture vectors.
>
> **One deliberate behavioural difference.** The seam is **fail-closed** where the companion falls back: a validated token that does not carry the named claim (or whose value the identity sanitiser refuses) is *rejected*, whereas the companion silently falls through to `sub` and then to the inner provider's value. For a correctly-configured Entra tenant the two never diverge, because every v2 token carries `oid` and `tid`. If your deployment relies on the fallback — for a federated flow whose tokens sometimes omit `oid` — that is the one thing to test before migrating. See [Claim mapping](../companions/auth-providers.md#claim-mapping-mapping-a-non-sub-identity).
>
> Reason 1 (the dual-button sign-up affordance via `EntraExternalIdAuthUI.wrap`) was **unchanged** when this note was written; the note immediately below closes it. This document is otherwise historical and is not being rewritten.

> **Second note added 2026-08-30 — reason 1 is closed too.** The dual-button affordance is now a first-class, vendor-neutral slot on the generic shell: `OidcAppConfig.SecondaryFlow` (a `Label` plus the extra authorize-request parameters that route the second journey), rendered by `OidcAuthUI` beside "Sign in" whenever it is declared. `OidcPresets.withEntraSignUpUserFlow <policyId>` is the Entra binding:
>
> ```fsharp
> let cfg =
>     OidcPresets.entraExternalId "<tenant>" "<client-id>" "<redirect-uri>"
>     |> OidcPresets.withEntraSignUpUserFlow "<sign-up-policy-id>"
> ```
>
> **The authorize request is the companion's, parameter for parameter.** `EntraExternalIdAuthUI`'s sign-up button called `beginSignInWithExtras oidcConfig [ "p", policyId ]`; the preset path issues the same standard OAuth / PKCE set with the same `p=<policyId>` appended, and the SDK test pack asserts the exact set rather than asserting that the parameter is merely present. Same redirect URI, same callback, same nonce binding back to that attempt.
>
> **One deliberate gap.** `SignInPolicyId` — routing the *primary* "Sign in" button through its own user-flow policy — has no generic equivalent: the slot is a SECOND flow, and the primary flow carries no extras. A deployment that relies on an explicit sign-in policy (rather than the app registration's default user flow) still needs the companion, or a `CustomAuthUI` wrapper of its own. See [Secondary flow](../companions/auth-providers.md#secondary-flow--the-sign-up-affordance) and [the migration](748-oidc-secondary-flow.md).

A follow-up SDK change adds either capability to the substrate (claim-remap seam on `OidcAuthProvider`; policy-routing variant of `OidcPresets.entraExternalId`); when that lands, the companion's last remaining use cases evaporate and the `0.Y.0` removal becomes safe. **Both landed on 2026-08-30** (the claim-mapping seam; the secondary-flow affordance), so the removal is unblocked apart from the `SignInPolicyId` gap the second note names.

## Verification

1. **`dotnet build`** — companion code stays compiling under 0.4.0. No `[<Obsolete>]` attributes are applied (avoids warning noise for consumers who keep the companion intentionally); the deprecation surface is README + module-doc only.
2. **Smoke-test sign-in** against your External ID tenant. Behaviour unchanged.
3. **Plan for 0.Y.0** — when you do migrate, the diff is mechanical per the worked examples above. The new path runs against the same External ID tenant + app registration; no Entra-side configuration changes required.

## Rollback

The deprecation is documentation-only at 0.4.0. There is nothing to roll back at the consumer end. Future-you wanting to migrate can follow this doc; future-you wanting to stay can ignore the README banners until the companion's `0.Y.0` removal lands.
