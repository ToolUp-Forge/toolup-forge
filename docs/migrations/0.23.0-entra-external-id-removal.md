# Migration — 0.23.0 EntraExternalId companion removal

**Status.** Removed in `0.23.0`. `ToolUp.AuthProviders.EntraExternalId` (server) and
`ToolUp.AuthProviders.EntraExternalId.Client` (client) no longer ship. This executes the removal
[`0.4.0-entra-external-id-deprecation.md`](0.4.0-entra-external-id-deprecation.md) scheduled as
`0.Y.0`; that document's worked examples are still the shortest description of the diff and this one
does not repeat them.

**Nothing changes on the Entra side.** The replacement path runs against the same External ID tenant
and the same app registration, with the same redirect URI. There is no portal step in this migration.

## Why now

The deprecation named two use cases the single-call preset did not cover, and said the removal became
safe when both landed in the substrate. Both did, on 2026-08-30:

| Companion capability | Substrate replacement |
|---|---|
| `oid` -> `UserId`, `tid` -> `TenantId` claim remapping | `AuthConfig.ClaimMapping` on the generic `OidcAuthProvider` (`TOOLUP_OIDC_USER_ID_CLAIM` / `TOOLUP_OIDC_TENANT_ID_CLAIM` for an env-composed deployment) |
| Dual-button "Sign in / Sign up" shell routing a distinct user flow | `OidcAppConfig.SecondaryFlow`, rendered by the standard `OidcAuthUI`; `OidcPresets.withEntraSignUpUserFlow <policyId>` is the Entra binding |

Before deleting anything, both replacements were driven against the companion's **own** test vectors
with the companion still present, and every vector agreed. Those vectors are still in the SDK test
pack — they were ported, not discarded — so the behaviour this document promises stays asserted.

## The diff

### Client

```fsharp
// Before
let entraConfig =
    EntraExternalIdClientConfig.create "<tenant>" "<client-id>" "<redirect-uri>"

{ ClientConfig.defaults with
    AuthUI = CustomAuthUI { Wrap = EntraExternalIdAuthUI.wrap entraConfig } }

// After
let oidcCfg =
    OidcPresets.entraExternalId "<tenant>" "<client-id>" "<redirect-uri>"
    // only if you surfaced a "Sign up" button:
    |> OidcPresets.withEntraSignUpUserFlow "<sign-up-policy-id>"

{ ClientConfig.defaults with
    AuthUI = OidcAuthUI (OidcAppConfig.toClientConfig oidcCfg)
    AuthUIHandlers = [ OidcRegister.handler ] }
```

`CustomDomain = Some "login.mybrand.com"` becomes
`OidcPresets.entraExternalIdWithDomain "<tenant>" "login.mybrand.com" "<client-id>" "<redirect-uri>"`.

The scope set and `ValidateIdToken = Some true` are preset defaults, so neither needs restating. The
`AuthUIHandlers` entry is **not** optional on the generic shell: `AuthUIProvider` fails loudly at
startup if `AuthUI = OidcAuthUI _` is set with no handler carrying the `"oidc"` tag.

### Server

```fsharp
// Before
let cfg = EntraExternalIdConfig.create "<tenant>" "<audience>"
ServerApp.empty |> ServerApp.withAuth (EntraExternalIdAuthProvider.create None cfg)

// After — the SAME issuer the client side built, from one source of truth
let authConfig = {
    Issuer = Some oidcCfg.Issuer
    Audience = Some oidcCfg.Audience
    KeySource = JwksDiscovery oidcCfg.Issuer
    TokenLocation = BearerHeader
    ClockSkewSeconds = None
    AcceptedAlgorithms = None
    PreferOidWhenPresent = None
    ClaimMapping =
        Some {
            UserIdClaim = Some "oid"
            TenantIdClaim = Some "tid"
        }
}

ServerApp.empty |> ServerApp.withAuth (OidcAuthProvider.fromConfig None authConfig)
```

`OidcAuthValidator` replaces `EntraExternalIdAuthValidator` — same preflight, same
`.well-known/openid-configuration` probe, same `ServerConfig.SkipPreflight` bypass.

### Environment variables

The six `TOOLUP_ENTRA_EXTERNAL_ID_*` variables are gone. The replacements are the generic OIDC ones:

| Removed | Replacement |
|---|---|
| `TOOLUP_ENTRA_EXTERNAL_ID_TENANT` + `_CUSTOM_DOMAIN` | `TOOLUP_OIDC_ISSUER` — spell the issuer out (`https://<tenant>.ciamlogin.com/<tenant>/v2.0`, or `https://<customDomain>/<tenant>/v2.0`) |
| `TOOLUP_ENTRA_EXTERNAL_ID_AUDIENCE` | `TOOLUP_OIDC_AUDIENCE` |
| `TOOLUP_ENTRA_EXTERNAL_ID_CLOCK_SKEW_SECONDS` | `TOOLUP_OIDC_CLOCK_SKEW_SECONDS` |
| `TOOLUP_ENTRA_EXTERNAL_ID_SIGN_UP_POLICY` | no env equivalent — the sign-up flow is declared in code, via `withEntraSignUpUserFlow` |
| `TOOLUP_ENTRA_EXTERNAL_ID_SIGN_IN_POLICY` | none; see "What did not move" |

Add `TOOLUP_OIDC_USER_ID_CLAIM=oid` and `TOOLUP_OIDC_TENANT_ID_CLAIM=tid` to reproduce the claim
remapping on an env-composed deployment.

**These variables are now unread, not renamed.** Leaving them set does nothing and raises nothing —
they are no longer in the config registry, so the unknown-key validator does not know them either.
Delete them from your deployment configuration when you migrate.

## Two behaviour changes worth testing before you cut over

**1. The claim mapping is fail-closed where the companion fell back.** The companion walked a
candidate chain — `oid`, then `sub`, then the inner provider's already-sanitised value — so a
validated token that omitted `oid` (or carried one the identity sanitiser refused) still signed the
user in, under a *different* identity from the one you configured. The seam rejects that token
instead, naming the claim it could not honour. For a correctly-configured External ID tenant the two
never diverge, because every v2 token carries `oid` and `tid`. If your deployment relies on the
fall-back — a federated flow whose tokens sometimes omit `oid` — that is the one thing to test.
Either fix the token, or leave `ClaimMapping = None` and accept `sub`.

**2. `toolup.auth.entra.claim_parse_failed_total` is gone.** The companion emitted it when its
best-effort post-processing could not re-read an already-validated payload. The seam has no
best-effort path: an unreadable payload is a rejected request, counted under
`toolup.auth.validate.malformed_total` like any other. A dashboard or alert on the old series will
simply stop receiving points — repoint it before it reads as "the error stopped happening".

## What did not move

**`SignInPolicyId` — routing the *primary* "Sign in" button through its own user-flow policy.** The
secondary-flow slot is by definition a *second* journey, and the primary flow carries no extra
authorize parameters. A deployment that depends on an explicit sign-in policy, rather than the app
registration's default user flow, needs a `CustomAuthUI` wrapper of its own; the documented
extension point is unchanged, and the removed shell's source is in the history of this repository at
`src/AuthProviders/EntraExternalIdClient/EntraExternalIdAuthUI.fs`.

**`EntraExternalIdAuthProvider.readIdpClaim`.** The `idp` claim is still emitted on issued tokens; a
deployment wanting per-IdP audit attribution reads it from the request's bearer token in its own
audit decorator, which is what the helper's own documentation recommended for anything beyond a
read.

## Verification

1. **`dotnet build`** — a consumer still referencing either package fails at restore (`NU1101`), not
   at compile. That is the intended, loud failure; remove the `PackageReference` first.
2. **Sign in end to end** against your External ID tenant. The authorize request is the same
   parameter set, including `p=<policyId>` when a sign-up flow is declared.
3. **Check the resolved identity**, not just that sign-in succeeded — this is where a fall-back you
   were relying on shows up. Confirm `AuthenticatedUser.UserId` is the `oid` you expect, and that a
   token missing it is refused rather than silently signing in as `sub`.
4. **Preflight** — `OidcAuthValidator` should report the same issuer you configured.

## Rollback

Pin the previous SDK version. There is no in-place rollback: the packages are not published at
0.23.0 or later, so a consumer that cannot migrate stays on the last release that carried them.
